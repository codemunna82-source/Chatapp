# Deploying VOXO's backend to Render

Phase 12 (ARCHITECTURE.md §12) was left with an open question from the
very start of this project: no hosting target had been specified. This
covers deploying to Render — a real, working option that needs no server
of your own.

There are two paths below. Try the Blueprint first; if it hits a
validation error (see the note in `render.yaml` — its exact syntax
couldn't be verified against Render's live docs from this sandbox,
`render.com` is network-blocked here), the manual walkthrough does the
identical setup with plain dashboard clicks.

## 0. You'll need

- A Render account (free) — https://render.com
- A free MongoDB Atlas cluster — Render has no managed MongoDB, so this is
  a separate step. At https://www.mongodb.com/cloud/atlas/register:
  1. Create a free M0 cluster (any region close to wherever you deploy).
  2. Database Access → add a user with a real password (not "admin"/"password").
  3. Network Access → for a first deploy, allow access from anywhere
     (`0.0.0.0/0`) — Render's outbound IPs aren't static on the free plan.
     Tighten this later if you upgrade to a plan with a fixed IP.
  4. Connect → "Drivers" → copy the `mongodb+srv://...` connection string,
     put your real username/password in it, and add a database name at
     the end, e.g. `mongodb+srv://user:pass@cluster0.xxxxx.mongodb.net/voxo?retryWrites=true&w=majority`.

## 1a. Fast path: Blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Connect this GitHub repo, branch `claude/voxo-android-whatsapp-txghqq`
   (or `main` once merged).
3. Render reads `render.yaml` at the repo root and shows the two
   resources it'll create (`voxo-backend` web service, `voxo-redis` key
   value store). If it shows a validation error here instead, stop and use
   1b below.
4. Before applying, fill in the env vars marked "set during deploy" in the
   Blueprint's env var review screen:
   - `MONGODB_URI` — your Atlas connection string from step 0
   - `SEED_MASTER_ADMIN_EMAIL` / `SEED_MASTER_ADMIN_PASSWORD` — real
     values for the first login (see step 3 below)
   - `META_*` — leave blank; `META_MOCK_MODE=true` covers this until you
     have real Meta Cloud API credentials
5. Apply. `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` are generated by Render
   itself — real random values, not anything committed to the repo.

## 1b. Reliable fallback: manual dashboard setup

1. **New → Key Value** (Render's Redis-compatible store). Name it
   `voxo-redis`, free plan. Once created, copy its internal connection
   string (Render shows this on the instance's page).
2. **New → Web Service** → connect this repo.
   - Runtime: **Docker**
   - Dockerfile path: `backend/Dockerfile`
   - Docker build context: `backend`
   - Health check path: `/health`
   - Plan: Free (or Starter for no cold-start sleep)
3. Under that service's **Environment** tab, add every variable from
   `.env.example` (repo root) with real values:
   - `NODE_ENV=production`
   - `PORT` — leave unset; Render injects its own and `src/config/env.ts`
     already reads `process.env.PORT`
   - `CORS_ORIGINS=*` (or your admin origin, if you add a web client later)
   - `MONGODB_URI` — your Atlas connection string
   - `REDIS_URL` — the connection string from step 1
   - `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` — generate real random
     values yourself, e.g. `openssl rand -hex 64` run locally, twice
   - `JWT_ACCESS_TTL=15m`, `JWT_REFRESH_TTL=30d`
   - `META_MOCK_MODE=true`, leave the other `META_*` vars blank for now
   - `RATE_LIMIT_WINDOW_MS=60000`, `RATE_LIMIT_MAX=100`, `LOG_LEVEL=info`
   - `SEED_TENANT_NAME`, `SEED_MASTER_ADMIN_EMAIL`,
     `SEED_MASTER_ADMIN_PASSWORD` — real values for your first login
   - `SEED_DEMO_DATA=true` — since `NODE_ENV=production`, the seed script
     otherwise skips creating a demo contact/conversation to test chat with
     (that skip exists to protect a real customer's tenant, which this
     deployment isn't)
4. Deploy.

## 2. Verify it's actually up

```bash
curl https://<your-service>.onrender.com/health
curl https://<your-service>.onrender.com/ready
```

`/ready` checks the real MongoDB/Redis connections — a 200 here means
both are genuinely reachable, not just that the process started.

## 3. Create the first MASTER_ADMIN account

The seed script (`backend/src/scripts/seed.ts`) creates the demo tenant +
master admin from `SEED_*` env vars, but it's a one-off script, not
something the web service runs automatically on boot. Run it once via
Render's **Shell** tab on the service (or a one-off Job):

```bash
node dist/scripts/seed.js
```

With `SEED_DEMO_DATA=true` set, this also creates a demo WhatsApp account,
2 contacts, and a conversation with 2 messages — something to actually open
and chat in from the app instead of an empty inbox. Both parts are
idempotent: if you already ran this once (e.g. before setting
`SEED_DEMO_DATA`), just add the env var and re-run the same command — it
recognizes the admin account already exists and only backfills the demo
chat data that's still missing.

## 3b. (Optional) Enable Cloudinary for profile pictures + media caching

Without this, avatar upload returns a clear "not configured" error and
WhatsApp media always re-fetches from Meta on every view — both work fine
without it, this just makes them faster/more durable. To enable: Render
dashboard → your backend service → **Environment** → add `CLOUDINARY_URL`
set to exactly the value shown on your Cloudinary dashboard under "API
Environment variable" (`cloudinary://<api_key>:<api_secret>@<cloud_name>`).
Saving redeploys automatically — no seed re-run or other step needed.

## 4. Point the Android app at it

Once you have a real `https://<your-service>.onrender.com` URL, tell me —
I'll rebuild the APK (`.github/workflows/android-build.yml`, the
`workflow_dispatch` `api_url`/`socket_url` inputs) pointing at it instead
of the emulator-only default, so the app on your phone actually connects
end-to-end: login, chat, everything.

## Known limitation of the free plan

Render's free web service plan spins down after ~15 minutes of no
traffic and takes ~30-60s to wake on the next request — the first request
after idle will be slow, not broken. Upgrade to a paid plan to remove
this if it matters for your testing.
